# Deferred to v0.2

Contract semantics are frozen for v0.1. What is written here was found while
v0.1 was being finished, is understood well enough to state, and is deliberately
not being acted on. Each item says what was observed, what the cause is, and
what would have to change — not what the change should be.

---

## The probe cannot tell a kernel handshake from an application `accept()`

**Observed.** SP004 reports a negative `accept_window_ms` on targets that are
plainly still serving: the last connection it counts as accepted predates T0,
sometimes by hundreds of milliseconds, so the branch is
`accept_window_unmeasured` (INCONCLUSIVE) rather than a verdict. It shows up
whenever the target is saturated at T0 — most reliably on a synchronous worker
pool under SP005's concurrent in-flight load, where the serial accept probe is
starved behind the workers.

**Cause.** The probe measures one thing and calls it another. It opens a TCP
connection and treats the completed handshake plus a successful HTTP exchange as
"the application accepted at time t". Those are two events, and a listening
socket separates them: the kernel completes the handshake into the accept queue
on its own, and the application picks it up from there whenever it next calls
`accept()`. While the queue is draining normally the gap is a millisecond or two
and the conflation is harmless — 0.6–6.9ms on H1, 1.1–1.6ms on H2, measured in
the field note of 2026-08-27. When the queue is full, or the workers are all
busy, the gap becomes unbounded: the handshake succeeds, the application never
arrives, and the probe cannot see which of the two happened. A backlog that
absorbs the connection and a listener that accepted it look identical from
outside.

The same blind spot is why the window rule shipped in v0.1 classifies by
`started_offset_ms`. That rule works around the ambiguity rather than removing
it: it stops the verdict depending on a timestamp the probe cannot attribute,
but the probe still cannot attribute it.

**What v0.2 would have to change.** Distinguishing the two needs evidence the
current probe does not collect — the accept queue's own state, or a second
signal from inside the target, or a probe that can tell "connected but
unanswered" from "connected and served" without waiting out its full timeout.
Until one of those exists, INCONCLUSIVE is the correct verdict for the family
and the summary should keep naming which of the three ways it happened.

**Not to be confused with** the post-T0 reset classes settled in v0.1. Those are
a different mechanism: a connection the kernel really had handshaken, destroyed
by a listener closing. This one is a connection the kernel handshook that the
application never received. See `docs/field-notes.md`, "Where post-T0 resets
actually land", which was written to keep the two apart.

## `timeouts.overall` was a setting that bounded nothing

**Observed.** `Timeouts.overall` shipped with v0.1's development schema at a
default of 120s, was written into every fixture configuration and both published
sample configurations, and was read by nothing. `grep -rn overall src/` returned
the field declaration and no other line: no phase compared against it, no
watchdog was armed from it, no error mentioned it. A configuration setting it to
1s and a configuration setting it to 1h produced identical runs, and a run that
took ten minutes crossed it without a word.

**Cause.** The two walls that exist are per-phase — `timeouts.startup` around
readiness and `timeouts.shutdown` around the signal-to-exit window — and each is
enforced where the phase is awaited, because that is where there is something to
race against. `overall` was declared at the same time as a third, obvious-looking
member of the same set, but there is no single await for a whole run to hang
off: a run is an image pull, a network create, two container starts, a readiness
wait, a baseline burst, a long-request phase, a signal, an exit wait, and a
teardown, each with its own failure mode. Enforcing a bound across all of them
means choosing what the bound covers (the pull? the teardown?), what state the
report is left in when it fires, and which exit code that is — decisions nobody
made, because nothing forced them to be made. The field kept its default and its
documentation and never grew a body.

**What v0.2 would have to change.** It has been removed from the schema rather
than left in place, because leaving it would ship, a second time, a setting that
does nothing, and implementing it inside v0.1 would be new behaviour against
frozen semantics. `loader` now names it: a configuration that still sets
`timeouts.overall` is a configuration error, exit 2, with a message saying the
setting is not in this version and what does bound the run. `extra="forbid"`
would already have refused it, but as "Extra inputs are not permitted", which
reads as a typo rather than as a removal.

Bringing it back means answering the questions above first. A wall around the
whole run is worth having — a target that never becomes ready is caught by
`timeouts.startup`, but a run that stalls in a pull, or in teardown, or in the
baseline burst against a target that answers slowly forever, is caught by
nothing. The shape that fits what is already here is a deadline started at the
first phase and checked at each phase boundary, firing as an infrastructure
error (exit 3) that names the phase it fired in, rather than a signal that
interrupts wherever it lands. That is a design, not a patch.

**Not to be confused with** `contracts.startup.budget`, which is a threshold and
only warns, or with `timeouts.startup`, which is a wall and aborts the run with
exit 3 and nothing measured. Both of those are enforced. See the comment in
`Timeouts` for why the field's absence is deliberate, and `docs/field-notes.md`,
"The startup wall, and the measurement that chose it", for the reading behind
the 90s value.

## `startup_resolution_ms` counts an interval this measurement never spends

**Observed.** `startup_resolution_ms` is `container_start_overhead_ms` plus one
`READINESS_POLL_INTERVAL_MS`, and it is the band SP001 resolves every budget
comparison against. On the fixture built to sit inside that band, the readiness
stage contributed **0.6–1.6ms** of the measured startup over ten runs on H1 and
1.3ms on the CI runner: readiness passed on its first probe every time, so the
100ms the resolution adds for sampling was never spent. The whole of the
measured duration was the TCP wait — 152.1–221.3ms of a 152.8–222.2ms startup on
H1, 258.3ms of 259.6ms on CI — and `wait_for_tcp` samples on a 50ms grid that
the resolution does not mention.

**Cause.** The two terms describe different clocks. `container_start_overhead_ms`
is the daemon's create/start round trip, measured *before*
`container_started_ns`, which is where the interval SP001 judges begins. So the
band's width is a cost that is not inside the thing being measured, while the
sampling that does quantize the measurement — 50ms in the TCP stage, 100ms in
the readiness stage — is represented by one interval of one of the two stages.
The definition is defensible as a floor on how precisely a budget can be
compared, and it is not a description of this measurement's own resolution.

The consequence is that the band's width and the value inside it are
independent: the daemon round trip can stay flat while the target's boot time
moves by a poll step, or move while the boot time does not. That is what removed
`SP001.within_resolution` from live coverage on 2026-09-03. Across 37
measurements on two hosts the row that covered it never got further than 52.8ms
from an edge, against a poll step of 100ms and an observed excursion of +255ms,
and no budget value reaches 55ms — so it was reclassified `decision_unit` rather
than recalibrated. See `docs/field-notes.md`, "The band that is not the
measurement's own resolution".

**What v0.2 would have to change.** Either term could be made to describe the
measurement it belongs to: a resolution built from the sampling actually spent
in the interval (the TCP grid, plus the readiness grid only when a probe is
retried) and the overhead dropped, since it lands outside the interval; or the
overhead kept and the interval it bounds started at the create request rather
than at `container_started_ns`. Both change what `within_resolution` means, and
so both are contract semantics.

Making `READINESS_POLL_INTERVAL_MS` configurable is a third option and a worse
one: on this measurement path a coarser interval would widen the published band
without moving the measurement at all, which is the instrument claiming a
resolution it does not have.

**Not to be confused with** `contracts.startup.budget`, which is a declared
threshold rather than a measured floor. The budget was not what went wrong here:
it was already within 3ms of the value that maximises the worst-case margin
across both hosts.
